# Verify Concilium

Every check here runs offline. No API keys, no network, no real `claude`/`codex`/`gemini`/`opencode`/`gh` binaries, and nothing reads or writes your home config.

## Commands

Run from the repo root. This is the same sequence CI runs (`.github/workflows/ci.yml`).

```bash
npm ci                                       # clean install from the lockfile
npm run build                                # core, then cli (tsc)
npm run typecheck                            # core + cli project refs and tests, desktop --noEmit
npm test                                     # vitest in cli, core, desktop, then the repo invariants
npm run lint -w concilium                    # eslint in desktop (warnings are allowed, errors are not)
node packages/cli/dist/bin/concilium.js --help   # the built CLI starts
```

All six commands must exit 0. A change is not verified until they do. To be sure nothing depends on your working tree, run them in a fresh clone:

```bash
rm -rf /tmp/concilium-verify
git clone --branch <branch> <repo> /tmp/concilium-verify && cd /tmp/concilium-verify
```

Faster loops while working:

```bash
npm run test -w @concilium/core              # core only
npm run test -w @concilium/cli               # cli only (needs a built core)
npm run test -w concilium                    # desktop only (needs a built core)
npm run test:repo                            # repo invariants only (needs a built core)
npx vitest run packages/core/src/services/deliberation-service.test.ts
npx vitest run packages/core/src/domain/code-council/   # playbooks, classifier, rubric, playbook-step check, ranking, judge choice (picked and configured) and parsing, graft parsing, synthesis.md, settling a divergence, divergence and reframe questions, dissent records, warning dissent and the mergeable block, the decisions.tsv format and the trail audit, PR verdict rules, the ship source, verifier choice with the same-family fallback and the same-family opt-in, OpenCode author and verifier families from the model id, the draft reason and the PR body, the factory task list, its order and its stop rules, the ledger's implementer outcomes, win rates, minimum sample and cross-family candidate sets
npx vitest run packages/core/src/domain/verification/ packages/core/src/adapters/gate-runner.test.ts   # gates, verify.yaml, integrity checks, validity rule
npx vitest run packages/core/src/adapters/git-worktree-workspace.test.ts   # worktrees, a pinned base, commits, revert, patch and mergeability check (against HEAD or a given target), gc
npx vitest run packages/core/src/services/code-service.test.ts   # candidates, verification, the adversarial round, reports, ranking, synthesis, grafting before a reframe, reframe, dissent (a quarantined test as a non-blocking warning), configured roles and the decision trail on real temp repos
npx vitest run packages/core/src/domain/roles/ packages/core/src/services/role-service.test.ts   # role specs, factory.yaml roles, --role flags per command, precedence, the role map, the verifier role and the same-family opt-in (flag, factory.yaml, saved), and the role rules (one rejecting case per rule id, the C4 cross-family rules, OpenCode families from the model id, the opt-in table)
npx vitest run packages/cli/src/commands/code.test.ts            # concilium code end to end on fake CLIs, open dissent and warnings in the summary, the decision trail and concilium trail check, concilium roles and config set verifier, role rule errors that stop before any fake CLI is spawned, and concilium stats over every run the file made, checked against each decisions.tsv (needs a built core; its cases share one repo and run in order, so run the whole file, not one case with -t)
npx vitest run packages/core/src/services/action-gate.test.ts packages/core/src/adapters/cli/agent-env.test.ts   # autonomy tiers, gates on a fake bare remote, approve and reject, keyed gates reused or superseded, agent CLIs without push credentials
npx vitest run packages/cli/src/commands/gates.test.ts           # concilium gates, approve and reject end to end (needs a built core)
npx vitest run packages/core/src/domain/code-council/shipping.test.ts packages/core/src/services/pr-service.test.ts   # verdict rules, verifier family and the same-family fallback, the ship commit without the trail, verify-pr, the SHA-pinned push and PR gates, reused and superseded gates, single-candidate runs and the void verdict on real temp repos with a fake bare remote
npx vitest run packages/cli/src/commands/pr.test.ts              # concilium pr, verify-pr and status end to end on fake CLIs, a fake gh and a fake bare remote: the pushed SHA, a second pr, the same-family warning and draft, --role verifier= (an author-family verifier refused before verifying, and verifying flagged as a draft with --allow-same-family-verifier, factory.yaml or saved config), a single-candidate run (needs a built core)
npx vitest run packages/core/src/domain/code-council/factory.test.ts packages/core/src/services/factory-service.test.ts   # the factory: task list validation, dependency order, the stop rules, two stacked and verified code runs, a stopped chain and a rejected list on real temp repos
npx vitest run packages/cli/src/commands/factory.test.ts         # concilium factory and concilium status <factory-id> end to end on fake CLIs: stacked mergeable, isolated reviewer flags, the same-family verifier opt-in (needs a built core)
npx vitest run packages/core/src/domain/code-council/ledger.test.ts packages/core/src/services/ledger-service.test.ts   # the learning ledger: implementer outcomes, the other roles' rows, win rates, the minimum sample, cross-family candidate sets, listing saved code runs
npx vitest run packages/core/src/domain/agent/providers.test.ts   # agentFamily: OpenCode's family from its model id, unknown vendors stay unknown
npx vitest run packages/core/src/adapters/cli/   # drivers on fake binaries, their argv, and the isolated reviewer flags (claude --safe-mode, codex --ignore-user-config --disable=hooks --disable=plugins, opencode --pure)
```

The CLI tests, the desktop tests and the repo invariants import `@concilium/core` (and `@concilium/core/providers`) from `packages/core/dist`. After changing core, run `npm run build:core` before them.

## How the offline harnesses work

- **Deliberation e2e** (`deliberation-service.test.ts`) builds a real `DeliberationService` with a real `CliCouncilGateway` and swaps only the agent CLIs: every driver is a `FakeCliDriver` whose `respond(brief)` answers by role. A Stage 1 brief gets a fixed plan or an error. A council brief (its task names `council-prompt.md`) reads that file from `brief.cwd`: a ranking prompt (it ends with "provide your code review and ranking") gets a ranking that puts the preferred plan first; anything else is the chairman and gets a fixed synthesis. Don't key on `FINAL RANKING:`, since the synthesis prompt quotes the juror rankings. Config, secrets and run history use the real `JsonConfigStore`, `PlaintextSecretStore` and `JsonRunRepository` in a `mkdtemp` directory. `OPENROUTER_API_KEY`, `COUNCIL_MODELS`, `CHAIRMAN_MODEL` and `OPENROUTER_API_URL` are stubbed empty so the temp config is the only source, and no key is set. To test a new pipeline behavior, add a case there and assert on the returned `RunRecord`, the recorded events, the briefs in `driver.runs`, or what `JsonRunRepository` reads back.
- **Through the composition root** (`config-service.test.ts`, `create-concilium.test.ts`, `role-service.test.ts`): `createConciliumRuntime` with real JSON stores in a temp dir, and every entry of `runtime.drivers` replaced by a `FakeCliDriver`, including the CLIs the test does not run (set `detection: { installed: false }`), because the runtime calls `detect()` on every driver when it fills in a default council, default agents or default implementers. `fetch` is stubbed with `vi.stubGlobal` to act as OpenRouter (SSE for streaming juror calls, JSON for the chairman) and records every request. Use this when the behavior depends on runtime wiring, the default council, the default agents, role resolution or the real `OpenRouterGateway`.
- **Roles in tests** (`role-service.test.ts`, `code-service.test.ts`, `code.test.ts`, `concilium.test.ts`): for resolution, make a temp repo dir with a `.git` directory (it bounds the upward search for `.concilium/factory.yaml`; without one the search walks up to `/`), write `factory.yaml` there, save roles with `runtime.configService.saveRoles(...)`, build flags with `parseRoleFlags([...])` (or `parseCommandRoles(command, { roles, agents })` for a command's scope), and stub `COUNCIL_MODELS`/`CHAIRMAN_MODEL` empty. For a code run, pass `roles` to `runCodeCandidates` as `{ ...defaultCodeRoles(['claude', 'codex']), judge: { value: 'codex:gpt-5.2', source: 'flag' } }` and assert on `record.roles`, the driver that ran (`driver.runs`, and `opts.model` for the role's model), `Judgment.judge`/`sameFamily`/`sameFamilyReason`, `synthesis.picker`, each graft's `integrator`, and `adversarial.adversaries` (`lane`, `provider`, `model`, `peers`). An adversary of a family no candidate has attacks every candidate, so its tests count for all of them; make them regression guards (pass on the base) when the test needs them counted. The verifier is resolved by `runtime.resolveVerifier` (no detection) and passed to `verifyPr` as `verifier`; it is not part of `CodeRoleMap`. In `code.test.ts` the `roles` cases use their own repo (`roles-repo`) so its `factory.yaml` reaches no other case; restore the file with `git checkout` after making it invalid, and delete `$XDG_CONFIG_HOME/concilium` after `config set`, since the CLI cases share the sandbox config. A configured judge or verifier in a CLI case must pass the role rules (a judge of a family with at most one implementer, a verifier outside every implementer and integrator family), or the command stops before the run.
- **The role rules in tests** (`roles.test.ts`, `code.test.ts`, `pr.test.ts`): a new rule id in `ROLE_RULES` needs a row in the `role rules` case table of `roles.test.ts` (rule, source, `at`, and a thunk returning the violations of a config that breaks only that rule; wrap a throwing call in `violations(() => ...)`); the table is checked against `Object.keys(ROLE_RULES)`. The integrator is the base's CLI (or the configured `integrator` role) on a code brief whose task starts with `You are integrating`, run in the worktree named `integration`; read the graft id from the `Graft graft-<n>:` line and write that graft's files, so a test can seed a graft that breaks a gate. The grafts are re-verified with the same gates and, when the test gate passes, the `evidence`/`regression-guard` adversarial tests (plus the conflicting tests of a `disjoint-survival` divergence), so a seeded breaking graft is rejected with gate evidence (and a test regression when a valid test passed before). A plain synthesis test must not diverge: keep one candidate failing no adversarial test of another family (or no adversarial round); a `disjoint-survival` run goes through synthesis too but adds `synthesis.divergence` and may end in `reframe-needed`, and any other trigger skips synthesis. A test that expects `mergeable: true` must also leave no open dissent on an acceptance line: no valid test failing at the integration head (a `quarantined` test is only a warning and does not block). Assert on `record.synthesis` (`base`, `branch`, `headSha`, `picker`, `notes`, `dropouts`, each graft's `status`, `commitSha`, `revertSha`, `reason`, `evidence` and `integrator`, `checks`, `patchPath`, `mergeable`, `mergeBlock`, `mergeCheck`, `divergence`), on the integration branch's history (`git rev-list base-head..integration`) and files, on `result.patch` (`git apply --check` in the checkout) and on the text of `synthesis.md`. With a `trail` (always in the CLI), the integration branch has one more commit on top, the decision trail: compare `synthesis.headSha` with `<branch>~1`, not with the branch head.
- **Reframe in tests** (`reframe.test.ts`, `synthesis.test.ts`, `code-service.test.ts`, `code.test.ts`): the divergence check runs only with `synthesis: { runDir }` and a type other than `prototype`, after ranking. To make `disjoint-survival` fire end to end, give two candidates of different families code that both pass the gates and have each family's adversary write a test the other candidate fails (a `run-tests.js` test gate, `judge: false` so the order is fixed): each test fails on the base and passes only on its author's candidate (`own-family-only`). Since grafting runs first for `disjoint-survival`, the outcome depends on the integration head: to end in `reframe-needed`, make the two candidates two readings of one line, so no graft can satisfy both tests (the picker gives no answer, or the integrator rewrites the base's reading, so the graft makes no change); to end `done`, make them complementary halves of two lines and have the picker name the other half and the integrator write code that passes both tests. The phraser is the planner (by default the first agent's CLI and model) on a plan brief whose `council-prompt.md` starts with `You are phrasing spec questions`; answer `{"questions": [{"clause": "<line exactly as listed>", "question": "..."}]}`, or an error to get the fallback. In `code.test.ts` an `AMBIGUOUS` file committed to the repo switches the fakes to the two readings (`claude` `-`, `codex` `_`, also as the integrator, so its graft of codex's `slug.js` makes no change), so that case runs last in `concilium code`. For `no-gate-pass` and `judge-spread` use `detectDivergence` directly with `DivergenceCandidate`s, tests, a matrix and `Judgment`s, and `settleDivergence` directly for the gate and test rules at the integration head. Assert on `record.status`, `record.reframe` (`divergence` with `trigger`, `detail`, `conflicts` and `tests`; `questions`; `phraser`; `source`; `notes`; `reportPath`; `grafting`), on `record.synthesis` (`divergence`, `checks` at the final head, `patchPath: null` when unresolved), that the integration branch exists but no `result.patch` does when unresolved, on the text of `reframe.md` and `synthesis.md`, on the prompt the phraser recorded, and on the CLI exit code (2).
- **Dissent in tests** (`dissent.test.ts`, `code-service.test.ts`, `code.test.ts`): dissent is collected on every code run, and `dissent.json` is written only next to a `synthesis.md` or `reframe.md` the run wrote (so a skipped synthesis without a reframe writes no file and no run dir). For the sources a run cannot produce yet (`base-pick`, `rubric-spread`), call `collectDissent` directly with a `Ranking` whose `judgments` you build (a `PASS` judgment over the winner whose `totals` put another candidate first; two `PASS` judgments of the same candidates with scores more than 3 apart) and `heads` mapping candidate ids to SHAs. For a blocking record in a pure test, use an `evidence` test that fails in `synthesis.checks.tests`; a `quarantined` test only gives a warning. End to end, a rejected graft gives an `overruled` record (seed a graft that breaks a gate, as in `runCodeCandidates synthesis`), an adversary writing a test that throws everywhere gives a `quarantined-test` `warning` that leaves the mergeable label alone, a conflicting test still failing at the integration head gives an `adversarial-test` record that blocks it, and a run with only the tied families installed gives `same-family-judge` records for the judge and the picker. Count every source when asserting the whole list: a same-family picker or judge adds `accepted-risk` records. Assert on `record.dissent` (`path`, `records` with `id`, `source`, `summary`, `evidence`, `acceptanceClause`, `resolution`, `resolutionReason`, `rationales`), on `synthesis.mergeable` and `synthesis.mergeBlock`, on `dissent.json` (`{version: 1, runId, records}`), on the `## Dissent` section at the top of `synthesis.md` and `reframe.md`, and in the CLI on the key order of the JSON record and the summary lines right after `Run <id> in <repo>` (open records, `Not mergeable:`, then `Warning:` lines). The dissent id of a warning depends on the sources before it, so match it with `dissent-\d+` in CLI tests.
- **The decision trail in tests** (`trail.test.ts`, `code-service.test.ts`, `code.test.ts`): `runCodeCandidates` writes the trail only with `trail: { runDir }` (the CLI always passes the run dir), so existing core cases without it are unchanged; pass the same `runDir` as `synthesis` so `file:` pointers (`rubric.json`, `synthesis.md`, `reframe.md`, `dissent.json`, `result.patch`) resolve. Run `checkTrail(runDir)` for the evidence: it resolves `commit:` pointers in the repo of the `run-start` event, so the temp repo must still exist. To test the check, write a forged line with `formatDecisionRow` (a row with an unknown `event`, or a copy of a real row with one field changed) and append it to `decisions.tsv`. For the commit, assert on `git show --name-only <branch>` (only `.concilium/runs/<id>/...`), `git show <branch>:.concilium/runs/<id>/decisions.tsv` against the run dir's file, `<branch>~1` against `synthesis.headSha`, and that `result.patch` does not mention `.concilium/runs`; with `commit: false`, the branch head is `synthesis.headSha`. Use `auditTrail` directly (with a `resolves` callback) for rule-by-rule cases.
- **Fake agent CLIs on `PATH`** (`subprocess.test.ts`, `cli-drivers.test.ts`, the four driver tests, `concilium.test.ts`, `code.test.ts`, `pr.test.ts`, `factory.test.ts`): write a small Node script named after the binary into a `mkdtemp` dir and make it executable (`0o755`). For reuse and supersede, pass the same `key` (a SHA) twice, then another key, and assert on `reused`, `superseded` and the statuses in `listGates`.

Assert on `prVerdict` (`branchHead`, `headSha`, `trailSha`, `verifier.sameFamily`) and `pr` (`sha`, `draftReason`) in `run.json`, `verification.md`, `pr-body.md`, the gate entries, the remote's refs, the fake `gh` log and the `status` text (`valid`, `void: ...`, `Warning: same-family verification: ...`).

## When to add or update tests

- **Changed a CLI flag, command or description:** run `npx vitest run packages/cli -u`. Read the snapshot diff and confirm every line of it was intended, then commit the `.snap` file with the change. Run it again after the last wording change, so the committed snapshot matches. Update `packages/cli/README.md` (options table) and any doc that shows the command, or `npm run test:repo` fails. Keep a command description short enough to fit on one line in the top-level `--help` list (about 45 characters now that `verify-pr [options] <run-id>` sets the column; a longer usage, such as `factory [options] <spec-file>`, widens the column and wraps another command's description): a wrapped line reads as another command to the docs check, which then reports `concilium <word>` as undocumented. A new command also goes in the list of registered commands in `concilium.test.ts` and must be mentioned in `AGENTS.md`, `README.md` and `packages/cli/README.md`.
- **Changed deliberation, ranking, prompts, the council or persistence:** add or extend a case in the offline e2e or a co-located unit test (`file.ts` → `file.test.ts`). Default-council rules go in `council-members.test.ts`; how the runtime applies them goes in `config-service.test.ts`.
- **Changed a role, its validation, its keyword, its default or the precedence:** extend `roles.test.ts` (pure) with a case that must pass and one that must be rejected (naming the rule id and the config path), then `role-service.test.ts` for the layer order and where the file is found. A change to which judge or adversary runs goes in `code-service.test.ts` (the configured judge, adversary, picker and integrator cases) and must keep a judge of a family it reads flagged `sameFamily` with its reason: in core the cross-family rule is a flag, never silently another CLI. A change to the role table, the warnings or the error exits goes in the `roles` cases of `code.test.ts`; a change to the jurors or chairman from `factory.yaml` in `concilium.test.ts`; a change to the verifier role in `role-service.test.ts` (`resolveVerifier`), `shipping.test.ts` (`pickVerifier`) and `pr.test.ts` (`--role verifier=`).
- **Added or changed a role rule** (`ROLE_RULES`, a severity, a hint, `checkRoleFamilies`, `parseCommandRoles`, `ROLE_COMMANDS`): add or update its row in the `role rules` table of `roles.test.ts` (the table must cover every key of `ROLE_RULES`), with a config that breaks only that rule and, for a family rule, a neighbouring config that must pass (a false error stops a valid run before it starts, a miss lets a family judge or verify itself). Keep every command checking the rules before any agent CLI runs: the `spawn.log` assertions in the `roles` cases of `code.test.ts` and the refused verifier in `pr.test.ts`. Update the rule table in `packages/cli/README.md` (`concilium roles`) and the role validator paragraph in `AGENTS.md`. Turning an error into a warning or back, letting a configured judge judge only its own family, or letting a configured verifier of an author family through are product decisions (layer 3 C4): ask before changing them.

## Rules for tests

- Assert on public outputs: the `RunRecord` or `CodeRunRecord`, the events emitted, the briefs a driver received, the files and branches written, the CLI's stdout, stderr and exit code. Don't assert on private helpers or call counts unless the count is the contract.
- Check that a new test catches a defect: break the code it covers once, see the test fail, then restore the code.
- No network, no real binaries, no `~`, no API keys: use temp dirs, fake CLIs on a `PATH` that holds only their temp dir, and pass `HOME`/`XDG_*` overrides to any spawned CLI (see `concilium.test.ts`).
- Silence the logger in tests that exercise noisy code: `beforeAll(() => setLogLevel('error'))`.
- New `.ts`/`.tsx` files need the MIT license header (see `AGENTS.md`); the repo invariants enforce it.
- Core source is scanned for imports by a regex, test files included: a string literal like `'… from '` followed by a quote in a core file reads as an import of an undeclared package, and so does a string that ends in `from` followed by a quote (`'… to graft from'`, or a test name such as `'... where each came from'`). Reword it (the diff parser uses a regex for `rename from`/`rename to` for this reason).
- In docs, a flag-like word inside a quoted example task (`concilium code "add a --dry-run flag"`) reads as a flag of that command to the docs check. Write the task without the dashes.
